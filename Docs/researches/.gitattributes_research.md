# .gitattributes 研究

## 场景与职责
`.gitattributes` 位于仓库根目录，是 Git 在“内容归一化/检出转换”阶段读取的仓库级策略文件。当前仓库只定义了 2 条规则，但它们覆盖了全仓文本文件的换行行为，核心职责是：

- 统一文本文件使用 LF，减少跨平台（Linux/macOS/Windows）提交时的 CRLF/LF 抖动。
- 对 `*.sh` 脚本做显式文本声明，保证 shebang 与 shell 解析在 LF 环境下稳定。
- 为自动化脚本链路（`.ops/*.sh`）提供一致的行结束符基础，降低执行失败概率。

从仓库上下文看，研究自动化链路（`.ops/research_guard.sh` -> `.ops/generate_research_blueprint_checklist.sh` -> `.ops/generate_daily_research_todo.sh`）均是 Bash 脚本，直接受 `*.sh text eol=lf` 规则保护。

## 功能点目的
当前文件内容：

```gitattributes
* text=auto eol=lf
*.sh text eol=lf
```

功能点拆解：

1. `* text=auto eol=lf`
- 对所有路径启用“文本自动识别 + LF 检出策略”。
- 目的：文本文件统一 LF；二进制文件维持 `-text`（不做换行转换）。

2. `*.sh text eol=lf`
- 对 shell 脚本强制标注为文本并指定 LF。
- 目的：避免脚本被误判导致行结束符不一致，降低 `/usr/bin/env bash` 执行异常风险。

## 具体技术实现（关键流程/数据结构/协议/命令）
Git 的生效流程可概括为：

1. 路径匹配阶段
- Git 按属性模式匹配路径，得到每个文件的 `text/eol` 属性。
- 在本仓库中，`*.sh` 会在通配规则基础上得到更明确的 `text` 属性。

2. 写入索引（add/commit）阶段
- 文本文件会按属性进行规范化写入索引（LF）。
- 这保证不同开发机提交到仓库的行结束符尽量一致。

3. 检出（checkout）阶段
- 文本文件检出为 LF（`eol=lf`）。
- 二进制文件保持 `-text`，不参与换行转换。

仓库内实测命令（用于复现/校验）：

```bash
git check-attr --all -- .gitattributes .gitignore README.md Script/run_devcontainer_claude_code.ps1
git check-attr text eol -- demo.gif CHANGELOG.md .ops/research_guard.sh
git ls-files --eol -- .gitattributes .gitignore .ops/research_guard.sh demo.gif
```

实测关键点：
- `.ops/*.sh` 显示为 `attr/text eol=lf`（命中 `*.sh` 规则）。
- `demo.gif` 显示 `i/-text w/-text`（虽有 `text=auto`，但仍被识别为二进制，不做文本归一化）。

## 关键代码路径与文件引用
- `.gitattributes:1-2`：仓库级行结束符策略定义。
- `.ops/generate_research_blueprint_checklist.sh:1-3`：Bash 入口与严格模式，依赖 LF 稳定执行。
- `.ops/generate_daily_research_todo.sh:1-3`：同上，属于日常执行链路。
- `.ops/research_guard.sh:166-173`：调用上述脚本形成研究流程主链。
- `Script/run_devcontainer_claude_code.ps1`：当前也受 `* text=auto eol=lf` 影响（并未单独声明 CRLF）。

## 依赖与外部交互
- 直接依赖：Git 属性引擎（`git add/checkout/merge` 等路径都会读取 `.gitattributes`）。
- 外部交互面：
  - 开发者本地 Git 与编辑器（跨 OS 的换行行为差异由该文件兜底）。
  - CI/自动化环境（检出后脚本执行的一致性）。
- 与其他配置关系：
  - 与 `.gitignore` 职责不同：`.gitattributes` 管“已跟踪文件内容表现”，`.gitignore` 管“未跟踪文件纳入范围”。

## 风险、边界与改进建议
风险与边界：

1. Windows 脚本兼容边界
- 当前未对 `*.ps1` 指定 `eol=crlf`，在极少数依赖 CRLF 的旧工具链里可能出现兼容问题。

2. 规则粒度较粗
- `* text=auto eol=lf` 覆盖全仓，若后续引入特殊文本格式（需要 CRLF），需额外加细分规则。

3. 二进制显式性不足
- 目前依赖 `text=auto` 自动识别。通常可用，但对特殊扩展名（非典型二进制）建议显式标注 `-text` 以降低误判概率。

改进建议：

1. 按需补充精细化规则
- 例如：`*.ps1 text eol=lf`（若坚持跨平台统一 LF），或明确约定 `*.ps1 text eol=crlf`（若团队以 Windows 生态优先）。

2. 增加关键二进制显式声明
- 如 `*.gif -text`、`*.png -text`、`*.jpg -text`，让策略更自解释。

3. 在仓库文档补一段“行结束符约定”
- 在 `README.md` 或贡献指南声明 LF 规范与校验命令，降低新贡献者理解成本。
